# Umbrella MVP: приложение

Backend на Go, веб-интерфейс на React и TypeScript, секреты в OpenBao, состояние и потоковые данные в PostgreSQL. Архитектурные документы MVP хранятся отдельно от репозитория.

Коннекторы, приём вебхуков и визуальный конструктор по плану из [`n8n.md`](../n8n.md): [docs/connectors.md](docs/connectors.md).

Вход через Microsoft Entra ID: [docs/entra-id.md](docs/entra-id.md).

Сопоставление групп LDAP / AD и Entra ID с ролями и командами: [docs/group-mapping.md](docs/group-mapping.md).

Хосты Zabbix и Prometheus, сопоставленные с КЕ: [docs/monitoring-hosts.md](docs/monitoring-hosts.md).

Резервное оповещение в Microsoft Teams и Zoom: [docs/teams-zoom.md](docs/teams-zoom.md).

Необязательная интеграция с Inventory DB (устройства как КЕ, статусы тревог обратно): [docs/inventory-db.md](docs/inventory-db.md).

Необязательная интеграция с Umbrella Flow (события трафика NetFlow / IPFIX / sFlow как инциденты, ссылка «Трафик» из инцидента и КЕ): [docs/flow.md](docs/flow.md).

Обработка в backend:

- **Секреты.** Единственное хранилище — OpenBao (KV v2, mount по умолчанию `umbrella`). Всё, что вводится в интерфейсе или API (секреты учётных данных, токены NetBox, ключи и токены PagerDuty, пароль SMTP, токен Telegram, verification token Zoom, секрет Entra ID, пароль PostgreSQL), сразу пишется в OpenBao, в приложении остаётся ссылка `openbao://…`. Там же хранятся хеши паролей локальных пользователей (PBKDF2-SHA256, путь `users/<id>`). Значения читаются при использовании и кешируются на 30 с, поэтому ротация в OpenBao не требует изменений в Umbrella. Вход по AppRole или токеном, продление токена. При удалении учётных данных их секрет удаляется из OpenBao.
- **Хранение состояния.** PostgreSQL обязателен. Конфигурация (КЕ, сервисы, команды, пользователи, роли, коннекторы, учётные данные, правила, окна, ТВ-панели, настройки, журнал аудита) хранится снимком в таблице `umbrella_state` (текущая и предыдущая версии, запись в одной транзакции) и сохраняется каждые 2 секунды и при остановке. Если текущий снимок не читается, берётся предыдущий; если не читается ни один, запуск останавливается с ошибкой, а снимок не перезаписывается. Инциденты и их хронология — в таблицах `alerts`, `alert_timeline`, `alert_keys`, решённые инциденты удаляются через 90 дней; запросы и события коннекторов — в своих таблицах (см. [docs/connectors.md](docs/connectors.md)). В `UMBRELLA_DATA_DIR` остаются только `umbrella.json` (подключение к OpenBao и PostgreSQL; пароль PostgreSQL — ссылкой на OpenBao), `setup-token` до завершения мастера и `sessions.gob` — сессии, поэтому после перезапуска пользователи остаются в системе. При старте Umbrella ждёт OpenBao и PostgreSQL до `UMBRELLA_STARTUP_WAIT`.
- **Приём.** `POST` или `PUT /api/ingest/{slug}` проверяет сеть, частоту, размер и учётные данные опубликованного коннектора, записывает запрос в PostgreSQL и отвечает 202 (или своим ответом узла `ack.response`); обработка идёт сразу после этого в фоновых обработчиках. Bearer-токен принимается в `Authorization: Bearer` или `X-Umbrella-Token`; есть также Basic, заголовок с секретом и HMAC-SHA256.
- **Приоритеты.** Важность инцидента — один из пяти приоритетов, единая таблица для движка, ТВ-панелей, карты CMDB, правил, порогов PagerDuty и резервного оповещения, интерфейса и сообщений; интерфейс показывает приоритет со словом («P1 · Критический»):

  | Приоритет | Значение `severity` в API | Название |
  |---|---|---|
  | P1 | `critical` | Critical / Критический |
  | P2 | `error` | High / Высокий |
  | P3 | `warning` | Medium / Средний |
  | P4 | `low` | Low / Низкий |
  | P5 | `info` | Informational / Информационный |

  В API, правилах, настройках и событиях хранятся прежние имена `critical`, `error`, `warning`, `info` и новое `low`, поэтому существующие данные не меняются. Счётчики по важности (ТВ-панели, CMDB) получили поле `low`; данные ТВ-панели содержат таблицу приоритетов `severities` (имя, приоритет, ранг, цвет, названия на двух языках). Синонимы в событиях: `p1`…`p5` и `sev1`…`sev5` в любом регистре; `low` — P4; `high` — P2; `average`, `medium`, `minor` — P3; `information`, `notice`, `not classified`, `debug` — P5. Пресеты: Zabbix 5 Disaster → P1, 4 High → P2, 3 Average → P3, 2 Warning → P4 (раньше — P3), 1 Information и 0 Not classified → P5; Alertmanager `severity=low` → P4. PagerDuty Events API v2 не знает уровня low, поэтому P4 уходит в PagerDuty как `info`.
- **Схлопывание и жизненный цикл.** Ключ = КЕ + сигнал (без сигнала — заголовок); важность = максимум по источникам; resolve, когда в норму вернулись все источники; повторное открытие в окне 10 минут; RED и USE одного сервиса связываются как «вероятная причина». Инцидент по КЕ, которой нет в каталоге, ждёт её и привязывается, когда она появляется: сразу при создании КЕ или псевдонима из карточки инцидента (`POST /api/incidents/{id}/create-ci`, `POST /api/incidents/{id}/bind-ci`), иначе в течение 15 секунд после изменения каталога (в том числе синхронизации NetBox). КЕ находится по ссылке Inventory DB из метки `source_ref` (если она указывает ровно на одну КЕ), затем по ID, имени, короткому имени, IP, DNS-имени из AD и псевдонимам, а если имя не нашло КЕ — по IP из метки `ip` (`PUT /api/cis/{id}/aliases`; псевдоним, которым уже называется другая КЕ, отклоняется с `alias_taken`). Если у КЕ уже есть активный инцидент по тому же сигналу, ожидавший инцидент присоединяется к нему и решается. Маршрут: КЕ → бизнес-сервис → команда-владелец → люди, без команды — ответственные за КЕ (см. «Кто получает инцидент»).
- **Rule Engine.** Правила RED и USE вычисляют PromQL по источнику метрик с интервалом правила (от 10 с до 1 ч). Серия выше порога дольше `for` даёт событие firing на КЕ из метки, возврат в норму или пропажа серии — resolved. Состояние серий сохраняется, поэтому перезапуск не теряет и не дублирует срабатывания.
- **PagerDuty Gateway.** Events API v2 (US или EU), `dedup_key = umb-<id>`, маршрут по команде и бизнес-сервису, ответственные КЕ в `custom_details`, порог важности. Выключенный PagerDuty — не ошибка: инциденты получают состояние `off` («PagerDuty не используется»), не считаются «не принятыми» и ничего не пишут в хронологию; после включения открытые инциденты отправляются в PagerDuty. Инциденты с меткой `umbrella_test=true` (тестовые события) в PagerDuty не отправляются. Ошибки доставки записываются в хронологию кодами (`no_key`, `key_unavailable`, `queue_full`, `breaker`, `unreachable`, `unavailable`, `rejected`, пропуск — `below_threshold`, `test`), интерфейс их переводит. Ошибки 429 и 5xx повторяются, остальные ошибки не повторяются; circuit breaker после 5 ошибок подряд на 60 секунд. Недоставленные trigger, acknowledge и resolve повторяются раз в минуту, в том числе после перезапуска. Webhooks v3 на `/api/pagerduty/webhook` проверяются по подписи, инцидент находится по `incident_key`, ID инцидента или алертам инцидента; события triggered, acknowledged, resolved, reassigned, escalated, annotated, priority_updated попадают в хронологию.
- **Резервное оповещение.** Открытый инцидент не ниже минимальной важности (по умолчанию error — P2), который никто не взял, получает отметку «Резерв»: при включённом PagerDuty — если тот не принял инцидент за время задержки (по умолчанию 2 минуты) или пропустил его по своему порогу; без PagerDuty резерв — основной канал и по умолчанию уходит сразу. Задержка и минимальная важность задаются в карточке «Резервное оповещение». Подтверждённые и решённые инциденты, инциденты в сервисном окне и тестовые события (`umbrella_test=true`) не оповещаются; оповещение, ещё ждущее отправки, отменяется при подтверждении (в хронологии — «Резервное оповещение отменено»). Люди маршрута и дополнительные адреса получают письмо и сообщение Telegram, каналы команд и дополнительные вебхуки — сообщение в Microsoft Teams (карточка с кнопками) и Zoom, со ссылками «Подтвердить», «Открыть» и Grafana; ссылка подтверждения (`/ack/<токен>`) подписана HMAC и действует 24 часа. Когда инцидент подтверждают (в Umbrella, по ссылке или в PagerDuty) или решают, все адреса, получившие резервное оповещение, получают короткое уведомление: кто и когда взял инцидент или что он решён, со ссылкой на него. До 3 попыток с паузой, результат каждой доставки попадает в хронологию; неотправленные оповещения и уведомления передаются снова после перезапуска.
- **Аутентификация и авторизация.** Сессии в HttpOnly-cookie `umbrella_session` (12 часов бездействия, не дольше 7 дней), для изменяющих запросов — заголовок `X-CSRF-Token` со значением `csrf` из ответа `/api/auth/login` или `/api/auth/me`. Локальные пароли, LDAP / AD и Entra ID (OIDC); блокировка после неудачных попыток входа; парольная политика со сроком действия. Каждый маршрут API проверяет разрешение `<страница>:<функция>`. API-токенов и сервисных учётных записей нет: API работает с той же сессией, что и интерфейс.
- **Разрешения.** Каталог разрешений (`GET /api/access/catalog`): `incidents` (view, ack), `cmdb` (view), `cis`, `services`, `maintenance`, `rules`, `credentials`, `teams`, `roles` (view, edit), `wallboards` (view, edit, proxies), `connectors` (view, edit, publish, payload), `netbox` (view, test, edit, sync), `monitoring` (view, test, edit, sync, link), `users` (view, create, edit, lock, password, delete), `settings.alerting` (view, test, edit), `status` (view, defaults), `settings.ldap` (view, test, edit), `settings.postgres` и `settings.openbao` (view, test, migrate), `settings.policy` (view, edit). Справочник `GET /api/refs` отдаёт разделы пользователей, ролей, команд и сервисов только тем, у кого есть разрешение страницы, которая их читает; остальные разделы приходят пустыми.
- **Область видимости.** Режим пользователя: «Все сервисы», «Сервисы моих команд» (владеют или поддерживают) или «Выбранные сервисы». Ограниченный пользователь видит только инциденты своих сервисов (список, счётчики, карточка, действия, Grafana, события на карте CMDB), создаёт сервисные окна и ТВ-панели только на свои цели и не может создать панель «все инциденты». Администратор видит всё всегда. Подробно — [docs/access.md](docs/access.md).
- **Кто получает инцидент.** Одна цепочка правил, её же показывает блок «Куда пойдёт инцидент» в карточках КЕ и сервиса (`GET /api/cis/{id}/route`, `GET /api/services/{id}/route`):
  1. **КЕ** события (метка `ci` или поле `ci`; ручные привязки хостов, имя, короткое имя, IP, DNS-имя).
  2. **Сервисы** этой КЕ, кроме выведенных, по порядку: критичность, действующие раньше планируемых, имя. **Основной сервис** — первый, у которого есть команда-владелец.
  3. **Команда-владелец** основного сервиса. Поддерживающие команды маршрут не меняют: они видят инциденты сервиса в области «Сервисы моих команд» и на ТВ-панелях своей команды.
  4. **Люди**: руководитель и участники команды (человек может быть в нескольких командах). Если у команды есть свой канал (ящик, чат Telegram, вебхук Teams или Zoom) — канал и руководитель. Нет людей — родительская команда.
  5. Нет сервиса с командой или людей — **ответственные за КЕ** (контакты NetBox или заданные вручную).
  6. **PagerDuty**: первая сверху строка маршрутов, у которой команда и сервис совпадают с командой и основным сервисом (пустое — любое), иначе интеграция по умолчанию. Резервное оповещение — люди из п. 4–5 плюс «Всегда оповещать также».
- **Grafana.** `/go/incidents/{id}/grafana` открывает дашборд из «Настроек → Оповещения» с окном вокруг инцидента (по умолчанию ±10 минут, до 24 ч) и переменными `var-incident`, `var-ci`, `var-ci_id`, `var-signal`, `var-service`, `var-team`; собственные параметры дашборда сохраняются. Ссылка работает для вошедшего пользователя с правом на инцидент, остальных отправляет к инциденту в Umbrella. Без настройки ссылка не показывается ни в интерфейсе, ни в PagerDuty и письмах.
- **Umbrella Flow.** `/go/incidents/{id}/flow` и `/go/cis/{id}/flow` перенаправляют на `<адрес Flow>/go/incident?ci=…&ip=…&ref=…&from=…&to=…` (RFC 3339): у инцидента — от 30 минут до открытия до текущего момента или до 10 минут после решения, у КЕ — последний час. Права и поведение без cookie — как у ссылки на Grafana; адрес — `GET/PUT /api/flow` (`settings.alerting:view` / `settings.alerting:edit`). Без адреса ссылок нет. Подробно — [docs/flow.md](docs/flow.md).

## Чего пока нет

- Реляционная схема конфигурации в PostgreSQL (сейчас она хранится снимком в одной таблице) и NATS JetStream вместо внутренних вызовов.
- Context Builder (генерация отдельного дашборда Grafana под инцидент).
- API-токены и сервисные учётные записи, метрики Prometheus (`/metrics`), просмотр журнала аудита в интерфейсе, уведомления в Microsoft Teams и Zoom.
- Pull-коннекторы (опрос источника по расписанию) и другие пункты плана из [docs/connectors.md](docs/connectors.md#что-из-плана-ещё-не-сделано).

Этих функций нет и в интерфейсе.

## Запуск

Нужны Go 1.26+, Node.js 22 (как в образе), OpenBao и PostgreSQL. Для разработки OpenBao поднимается в dev-режиме, PostgreSQL — например, из [deploy/postgres](../deploy/postgres):

```bash
cd app
make openbao-dev                 # контейнер OpenBao, KV v2 umbrella/, токен dev-root
make build
make run                         # http://localhost:8080, данные в backend/data
```

Адрес OpenBao (`http://127.0.0.1:8200`, токен `dev-root`, хранилище `umbrella`) и подключение к PostgreSQL вводятся в мастере настройки — `make openbao-dev` напоминает эти значения в конце.

Режим разработки с горячей перезагрузкой: `make dev-api` и `make dev-web` (интерфейс на :5173). Проверки: `make test` (`go vet`, `go test`, проверка типов интерфейса; тесты с PostgreSQL запускаются, если задана `UMBRELLA_TEST_POSTGRES`). Образ: `make image` (версия из `git describe`, коммит и дата сборки видны на странице «Состояние системы»). Запуск образа с томом данных: [deploy/umbrella](../deploy/umbrella).

При первом запуске открывается мастер настройки. Сервер пишет в журнал код установки (`setup_code`) и кладёт его в `UMBRELLA_DATA_DIR/setup-token` (или берёт из `UMBRELLA_SETUP_TOKEN`). Мастер сохраняет `umbrella.json`; после этого Umbrella при каждом запуске подключается к OpenBao и PostgreSQL из этого файла и без них не стартует. Если в базе нет состояния Umbrella, запуск останавливается с ошибкой: восстановите базу или удалите `umbrella.json`, чтобы пройти мастер заново.

### Быстрый старт: от установки до первого инцидента у дежурного

1. **Мастер** (7 экранов). Адрес Umbrella подставляется из адреса, по которому открыт мастер, и сохраняется (поправьте, если пользователи открывают Umbrella по другому имени). Парольная политика свёрнута в шаге «Администратор» и по умолчанию не требует решений.
2. **Вход.** На пустой странице «Инциденты» — чек-лист «Первые шаги» с прогрессом (он же карточкой на «Состоянии системы»). Каждый пункт ведёт на страницу, где он делается; пункты, на которые у пользователя нет прав, помечены «Попросите администратора». Чек-лист пропадает, когда выполнены все обязательные пункты.

| Пункт | Готов, когда | Куда ведёт |
| --- | --- | --- |
| Источник событий | опубликован хотя бы один коннектор | `/monitoring?connect=1` (диалог «Подключить источник»; без доступа к «Системам мониторинга» — `/connectors?connect=1`) |
| Первое событие | получено хотя бы одно событие (коннектором или правилом) | коннектор (если он один) или список коннекторов |
| Команда | есть команда хотя бы с одним активным участником | «Команды» |
| КЕ в сервисе (по желанию) | КЕ привязана к сервису с командой-владельцем | «Бизнес-сервисы» |
| Канал доставки | PagerDuty включён и есть ключ, **или** почта / Telegram / Teams / Zoom настроены и есть получатель (участник команды с адресом или чатом, свой канал команды, «Всегда оповещать также») | «Настройки → Оповещения» |
| Адрес Umbrella | задан публичный адрес | «Настройки → Оповещения», карточка «Адрес Umbrella» |

3. **Источник:** «Подключить» → тип (Zabbix, Alertmanager, Grafana, Graylog, Umbrella Flow, webhook) → «Создать»; токен, коннектор и публикация делаются сразу. В Zabbix — импорт готового способа оповещения с подставленными адресом и токеном, медиа пользователю, действие триггера. При ручном создании коннектора токен делается кнопкой «Создать токен» прямо в слоте учётных данных и показывается один раз с кнопкой «Скопировать».
4. **Команда:** «Новая команда» → название → «Добавить участников».
5. **Доставка:** включить PagerDuty и вставить ключ интеграции по умолчанию (или почта + дежурный ящик в «Всегда оповещать также»). Инцидент по КЕ, которой ещё нет в каталоге, уходит по маршруту по умолчанию.

API чек-листа: `GET /api/onboarding` (любой вошедший пользователь) → `{done, steps: [{id, done, optional, path, can_fix}]}`, id: `source`, `event`, `team`, `catalog` (optional), `delivery`, `public_url`. Адрес Umbrella: `GET/PUT /api/settings/public-url` (`settings.alerting:view` / `settings.alerting:edit`); форма PagerDuty его больше не присылает и не затирает. Токен из диалога коннектора: `POST /api/connectors/credentials/token` `{name}` (`connectors:edit` + `credentials:edit`) → `{credential, token}`.

**Сколько это стоит** (минимальный путь до инцидента у человека, без NetBox и мониторинга хостов):

| | Было | Стало |
| --- | --- | --- |
| Мастер | 8 экранов, 4 решения, публичного адреса нет | 7 экранов, 3 решения, адрес предзаполнен и сохранён |
| После входа | 9–11 экранов на 6–7 страницах, ~40 действий (24 без CMDB), подсказок нет | 4 экрана на 4 страницах (чек-лист, «Подключить источник», «Команды», «Оповещения»), 15 действий, каждый шаг — одна ссылка из чек-листа |
| Настройка Zabbix | 4 шага, адрес и токен переписываются руками | 3 шага, импорт YAML с подставленными адресом и токеном |
| Решения | 10–12 | 6 (3 в мастере; тип источника; PagerDuty или почта; команда) |
| **Итого** | **17–19 экранов, ~40 действий + 4 шага в Zabbix** | **11 экранов, 15 действий + 3 шага в Zabbix** |

### Пример

API работает с сессией: вход сохраняет cookie, а изменяющие запросы несут заголовок `X-CSRF-Token`. Пользователю нужны права `credentials:edit`, `connectors:edit` и `connectors:publish` (у администратора есть все).

```bash
J=cookies.txt
CSRF=$(curl -s -c $J localhost:8080/api/auth/login -d '{"username":"admin","password":"…"}' | jq -r .csrf)
api() { curl -s -b $J -H "X-CSRF-Token: $CSRF" "$@"; }

# учётные данные для приёма: секрет уходит в OpenBao
CRED=$(api localhost:8080/api/credentials -d '{"name":"Мой источник","type":"bearer","secrets":{"token":"s3cr3t"}}' | jq -r .id)
# коннектор из шаблона «универсальный webhook» с этими учётными данными, затем публикация
CON=$(api localhost:8080/api/connectors -d '{"name":"Мой источник","slug":"my","preset":"webhook","credentials":{"webhook.credential":"'$CRED'"}}' | jq -r .id)
api -X POST localhost:8080/api/connectors/$CON/publish -d '{}'

# приём: без сессии, с токеном из учётных данных
curl -X POST localhost:8080/api/ingest/my -H "Authorization: Bearer s3cr3t" \
  -d '{"id":"x1","host":"db-01","signal":"use.disk","severity":"critical","status":"firing","title":"Диск заполнен"}'
```

```
    *.tsx, *.ts            API-клиент, роутер, темы, локализация (i18n.tsx и strings.ts рядом со страницами), анимации, общие элементы интерфейса, редактор парольной политики
```

## Интерфейс

Компоновка рассчитана на инженеров мониторинга и дежурных:
- панель навигации слева (сворачивается кнопкой в верхней строке) с группами Обзор, Автоматизация, Организация и Настройки;
- верхняя строка: кнопка меню, логотип, меню пользователя (профиль, язык, тема, выход);
- над таблицами — плитки-счётчики; метки важности и статусов мягкие, с цветной точкой;
- карточки объектов открываются боковой панелью с вкладками; конструктор устроен как палитра узлов, холст и инспектор.

### Темы и языки

Встроены светлая и тёмная темы и два языка — русский и английский. Тема, язык и часовой пояс по умолчанию задаются в мастере и на странице «Состояние системы»; свой выбор пользователь делает в меню пользователя, он хранится в браузере (localStorage). Загрузки своих тем и языков нет. Данные с сервера (названия КЕ, инцидентов, правил, записи хронологии) показываются как есть.

### Анимация

Смена темы раскрывается кругом от точки щелчка (View Transitions API; в браузерах без него цвета меняются плавным переходом). Анимированы появление страниц и шагов мастера, меню, панелей и окон. Если в ОС включено уменьшение движения, анимация отключается.
